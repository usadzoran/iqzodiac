# تقرير التدقيق الأولي — IQZodiac

**التاريخ:** 2026-11-01  
**المستودع:** `usadzoran/iqzodiac`  
**النشر الحالي:** GitHub Pages — `https://usadzoran.github.io/iqzodiac/`  
**قاعدة البيانات:** مشروع Supabase `Zodiaque`، الحالة `ACTIVE_HEALTHY`

## 1. نطاق التدقيق

تم فحص بنية المستودع، صفحات HTML، ملفات JavaScript وCSS، مسارات الخادم، ترحيلات قاعدة البيانات المطبقة، الجداول العامة، سياسات RLS، وظائف Edge المنشورة، التخزين، وقائمة TODO الموجودة في المشروع. لم يتم إنشاء جداول أو تغيير بيانات خلال هذا التدقيق.

## 2. ما هو موجود ويعمل أو متصل فعلياً

### الهوية والتنقل

- الهوية البصرية IQZodiac موجودة ومستخدمة عبر الصفحات، مع نظام ألوان وخطوط وقائمة تنقل مشتركة.
- الصفحات الحالية: الصفحة الرئيسية، التسجيل، تسجيل الدخول، الملف الشخصي، المساعد، Discover، Match، الرسائل، Daily، Rooms، YouTube، VIP، VIP Live، المحفظة، ومتجر الهدايا.
- دعم الإنجليزية والعربية موجود مع تبديل لغة واتجاه RTL في طبقة اللغة.
- GitHub Pages يستضيف الواجهة الأمامية، مع مسارات خادم محلية/متوافقة مع Vercel لبعض الوظائف.

### الحساب والمساعد

- صفحة إنشاء الحساب وتسجيل الدخول موجودتان ومربوطتان بعميل المصادقة الحالي.
- Trigger قاعدة البيانات `handle_new_user` ينشئ صفاً في `public.profiles` بعد إنشاء المستخدم.
- ملف الحساب يحفظ الاسم الأول، اسم العائلة، العمر، الهاتف، الاسم المستعار، المعرف، وإعدادات الخصوصية.
- المساعد يطرح أسئلة متتابعة، يجمع الاهتمامات وتاريخ الميلاد، يحسب البرج، ويحفظ التقدم والإجابات في `discovery_profiles` و`discovery_answers`.
- حقل التسجيل الحالي يختار تاريخ الميلاد من تقويم، ثم يحسب العمر للتحقق من شرط 18–120.

### المحتوى الاجتماعي والمطابقة

- Home feed متصل بعمليات المنشورات والتعليقات والإعجابات.
- Match يستخدم ملفات الاكتشاف وعمليات الإعجاب والتخطي والمطابقات المتبادلة.
- الرسائل الخاصة وطلبات كشف الوجه والموافقات الثنائية موجودة على مستوى الجداول وعمليات RPC الحالية.
- الملف الشخصي يحتوي على إعدادات الهوية والخصوصية وتفضيلات التوافق.

### Daily وYouTube

- Daily يجمع الطقس من Open-Meteo والأخبار من RSS عبر الخادم، مع انتهاء العناصر حسب اليوم وعدم حفظها في قاعدة البيانات.
- YouTube يستخدم مسار خادم للبحث، ويعرض المشغل الرسمي المضمن، مع إبقاء مفتاح API خارج JavaScript العام.

### VIP والمحفظة والبث

- جداول VIP والمحفظة والهدايا والسجلات والتقارير موجودة مع تفعيل RLS.
- الواجهة الحالية تقرأ حالة الميزة والمحفظة بشكل آمن، لكنها لا تدعي أن الدفع أو البث أو السحب يعمل فعلياً.
- مسار VIP الخلفي يغلق الوصول عند غياب جلسة موثقة أو دور خادمي مناسب.

## 3. ما هو موجود لكنه تجريبي أو ناقص

- غرف الصوت تعمل كواجهة محلية فقط؛ لا يوجد صوت حقيقي أو Realtime.
- مكالمات الصوت في الرسائل محاكاة بصرية ولا تصل إلى ميكروفون أو مزود اتصال.
- معاينات صور التسجيل والمعرض محلية؛ لا يوجد رفع فعلي لصور المستخدم إلى Storage.
- كشف الوجه في المحادثة يعتمد على طبقة موافقة، لكنه لا يملك نظام وسائط خاصاً مكتملًا.
- الإشعارات في الملف الشخصي محلية/واجهة حالية وليست نظام إشعارات مركزيًا لكل الأحداث.
- VIP Live موجود كـ scaffold؛ لا يوجد مزود WebRTC/HLS، تشغيل موقّع، دردشة Realtime، أو لوحة مذيع مكتملة.
- المحفظة والهدايا والدفع والسحب موجودة كهيكل وقواعد حماية، لكن لا توجد بوابة دفع أو webhooks أو عمليات مالية فعلية مفعلة.
- إعدادات VIP الحالية تعتمد على أدوار وقيم ميزات، لكن لا يوجد نظام اشتراك كامل بتاريخ بدء وانتهاء وصلاحيات شاملة.

## 4. وظائف غير موجودة أو غير مكتملة مقارنة بالمواصفات

- لا يوجد قسم Movies أو تكامل TMDB/مصادر بث مرخصة.
- لا يوجد قسم World News & Trends مستقل؛ الموجود هو Daily news محدود بمصدر RSS واحد.
- لا يوجد قسم Weather كامل باختيار مدينة يدوي وتفضيلات محفوظة للمستخدم؛ Daily يملك قراءة طقس حالية مع تحديد موقع اختياري.
- لا توجد ألعاب Sudoku أو Minesweeper أو Solitaire أو Ludo أو Chess أو Solitaire Battle.
- لا يوجد نظام ألعاب جماعية حقيقي، matchmaking للألعاب، سجل مباريات، دعوات، أو تحقق خادمي للحركات.
- لا توجد لوحة إدارة مخفية ومتكاملة لمالك الموقع لإدارة المستخدمين والمحتوى والمساعد والأخبار والألعاب والمعاملات والبث.
- لا يوجد بحث Match مكتمل حسب البلد والمدينة والعمر والتفضيلات المعلنة؛ الموجود هو ترتيب/عرض ملفات متوافقة من البيانات المتاحة.
- لا توجد حقول بلد ومدينة وإعدادات تفضيلات مواعدة مكتملة في `profiles`.
- لا يوجد تكامل Android/Social Hub، وهذا صحيح وفق المواصفات لأنه مؤجل لمرحلة التطبيق.

## 5. جرد قاعدة البيانات الحالية

### الجداول القابلة لإعادة الاستخدام

- الهوية: `profiles`
- الاكتشاف: `discovery_profiles`, `discovery_answers`
- الشبكة الاجتماعية: `posts`, `comments`, `post_likes`, `follows`, `daily_moods`
- التواصل: `conversations`, `conversation_participants`, `messages`, `face_reveal_consents`
- المطابقة: `match_likes`, `match_skips`, `matches`
- VIP والبث: `vip_user_roles`, `vip_live_sessions`, `vip_live_chat_messages`, `vip_live_reports`, `vip_moderation_actions`
- المحفظة والمدفوعات: `vip_wallets`, `vip_wallet_ledger`, `vip_coin_packages`, `vip_payment_orders`, `vip_payment_events`
- الهدايا والأرباح: `vip_gifts`, `vip_gift_transactions`, `vip_creator_earnings_ledger`, `vip_revenue_share_settings`, `vip_withdrawal_requests`
- الإدارة والحالة: `vip_admin_audit_log`, `vip_feature_status`
- صالون/حجز موجود كمنظومة مستقلة: `salon_owner_roles`, `salon_barbers`, `salon_appointments`, `salon_settings`, `salon_visitors`

جميع الجداول العامة التي ظهرت في الفحص مفعّل عليها RLS. توجد سياسات قراءة/إدخال/تحديث/حذف مقيدة حسب المستخدم أو الدور لكل من الحسابات، الاكتشاف، المنشورات، الرسائل، المطابقة، وميزات VIP.

### التخزين والوظائف

- يوجد bucket باسم `salon-media` وهو عام، ومخصص لمنظومة الصالون الحالية.
- لا يوجد bucket خاص واضح لصور ملفات IQZodiac أو الصور الخاصة وكشف الوجه؛ يجب عدم إعادة استخدام bucket العام للصور الحساسة.
- توجد Edge Function واحدة نشطة: `salon-create-barber` مع التحقق من JWT.
- لا توجد Edge Functions مخصصة بعد لعمليات الدفع، الهدايا، السحب، البث، الإشعارات، أو أدوات المساعد.

## 6. ملاحظات أمنية وتقنية مهمة

1. يجب فصل بيانات الصور العامة والخاصة في Storage بسياسات وصول منفصلة، وعدم وضع صور التحقق أو الصور الخاصة في bucket عام.
2. يجب تنفيذ العمليات المالية وتغيير الأرصدة وإصدار صلاحيات مشاهدة البث في الخادم فقط، مع idempotency وسجل تدقيق.
3. المساعد لا ينبغي أن يصل إلى الجداول مباشرة بصلاحيات واسعة؛ المطلوب وظائف Backend محددة مع تحقق جلسة وصلاحية وتأكيد للمستخدم قبل العمليات الحساسة.
4. يجب إضافة Realtime فقط للأقسام التي تحتاجه فعلياً، مثل الرسائل والبث، بعد تحديد سياسات القنوات والصلاحيات.
5. لا ينبغي تشغيل ميزات VIP أو الدفع أو البث قبل توفير مزودي الخدمة والمفاتيح والاختبار الحقيقي.
6. يجب إضافة حقول البلد والمدينة والتفضيلات فقط بعد تحديد نموذج البيانات النهائي وإعادة استخدام `profiles` أو جدول تفضيلات واحد، وليس إنشاء جداول مكررة.

## 7. ترتيب التطوير المقترح

1. تثبيت الحساب والملف الشخصي: البلد، المدينة، اللغة، تاريخ الميلاد، الصور الخاصة/العامة، وسياسات Storage.
2. إكمال البحث والمطابقة باستخدام البلد والمدينة والعمر والاهتمامات والتفضيلات مع احترام الحظر والخصوصية.
3. إكمال الرسائل وRealtime والإشعارات، ثم الموافقة الثنائية لكشف الصور والمكالمات عبر مزود حقيقي.
4. بناء أدوات المساعد المحددة والصلاحيات والتأكيدات وسجل العمليات، دون وصول مباشر غير محدود للقاعدة.
5. اختيار وربط مزود Live فعلي قبل تفعيل أي زر بث أو مشاهدة مدفوعة.
6. ربط الدفع والهدايا والسحب عبر webhooks وخادم آمن قبل عرض أي عمليات مالية.
7. إضافة Movies وWorld News الموسع وWeather المتقدم.
8. بناء الألعاب الفردية أولاً، ثم الألعاب الجماعية مع تحقق خادمي للحركات.
9. بناء لوحة الإدارة المخفية بعد تثبيت أدوار المالك وعمليات التدقيق.
10. اختبار شامل على حساب عادي وVIP، والهاتف، والشبكة، وRLS، وعدم وجود روابط أو صفحات مكسورة.

## 8. خلاصة المرحلة الأولى

المشروع ليس فارغاً ويحتوي على أساس اجتماعي ومصادقة واكتشاف ومطابقة ورسائل وVIP scaffold وDaily وYouTube. الجزء الأكبر من المنظومة المالية والبث والألعاب والإدارة ما زال غير مكتمل أو تجريبياً. قاعدة البيانات الحالية قابلة لإعادة الاستخدام ولا توجد حاجة لإعادة إنشائها. أي تطوير لاحق يجب أن يكون إضافياً ومحدوداً داخل الأقسام الحالية، مع migrations آمنة فقط عند الحاجة.
