# تدقيق المساعد الذكي في IQZodiac

**المستودع:** `usadzoran/iqzodiac`

**تاريخ التدقيق:** 2026-11-03

## النتيجة الرئيسية

المكوّن الموجود باسم **AI Assistant** يعمل حاليًا كمعالج onboarding ثابت داخل المتصفح، وليس كمساعد ذكاء اصطناعي محادثي. فهو يعرض 12 سؤالًا محددًا، ثم يجمع الاهتمامات وتاريخ الميلاد، ويحسب عنصرًا شخصيًا وبرجًا بطريقة قواعد ثابتة. لا توجد خدمة LLM أو API للمحادثة أو فهم سياقي حقيقي.

فحص JavaScript الحالي ناجح عبر `npm run check`، لكن نجاح الفحص النحوي لا يعني أن تدفق الحفظ والاستعادة مكتمل وظيفيًا.

## المشاكل المهمة في المساعد

### 1. خلل استعادة النتيجة بعد إعادة تحميل الصفحة — أولوية حرجة

عند اختيار إجابة جاهزة، يحفظ الكود نص الإجابة في `answer_choice`، ويحفظ عنصر الإجابة (`fire/earth/water/air`) داخل الذاكرة فقط. عند إعادة فتح الصفحة، تستعيد `hydrateFromDatabase()` قيمة `answer_choice` لكنها لا تستعيد `element`. بعد ذلك تحاول `tally()` التصنيف من `answer.text` فقط، بينما الإجابات الجاهزة لا تملك `text`، ولذلك قد تختفي نتيجة الشخصية أو تظهر `Undetermined` بعد refresh أو على جهاز آخر.

**المكان:** `assistant.js`، دوال `persistToDatabase()` و`hydrateFromDatabase()` و`tally()`.

**الإصلاح المقترح:** حفظ رمز العنصر في عمود مستقل مثل `answer_element`، أو إعادة اشتقاق العنصر من رقم السؤال ونص الاختيار عند الاستعادة. الأفضل تخزين معرف ثابت للاختيار بدل النص المترجم.

### 2. زر “Start over” لا يحذف الإجابات القديمة

زر البدء من جديد يفرغ الحالة المحلية ويكتب ملف الاكتشاف كـ `in_progress`، لكنه لا يحذف صفوف `discovery_answers` القديمة من Supabase. عند إعادة تحميل الصفحة، تعيد `hydrateFromDatabase()` قراءة الإجابات السابقة وتستعيدها، فيظهر للمستخدم أن إعادة البدء لم تعمل فعليًا.

**الإصلاح المقترح:** إضافة عملية حذف آمنة للإجابات الخاصة بالمستخدم والإصدار الحالي قبل بدء جلسة جديدة، أو استخدام `reset_token/session_id` يميز المحاولة الحالية. يجب تنفيذ ذلك عبر RPC أو عملية مقيدة بسياسات RLS، مع تأكيد واضح للمستخدم.

### 3. واجهة الحفظ تعرض النجاح حتى عند فشل الحفظ

`persistToDatabase()` يلتقط الخطأ ويكتفي بـ `console.warn`. في الوقت نفسه تعرض الواجهة دائمًا عبارات مثل “Saved to your account”. لذلك قد يعتقد المستخدم أن بياناته محفوظة بينما فشل الاتصال أو رفضت قاعدة البيانات العملية.

**الإصلاح المقترح:** إرجاع نتيجة الحفظ، وإضافة حالة واضحة: جارٍ الحفظ، تم الحفظ، تعذر الحفظ مع زر إعادة المحاولة. لا ينبغي إعلان النجاح قبل انتهاء عمليتي profile وanswers بنجاح.

### 4. الحفظ غير متزامن قبل الانتقال أو المغادرة

`saveState()` يستدعي `persistToDatabase()` من دون انتظار النتيجة. إذا انتقل المستخدم بسرعة إلى Match أو أغلق الصفحة، يمكن أن تضيع آخر إجابة. كما أن تحديث الملف والإجابات عمليتان منفصلتان وقد تنجح إحداهما وتفشل الأخرى.

**الإصلاح المقترح:** استعمال `await` قبل عرض النتيجة أو الانتقال، ويفضل تغليف تحديث الملف والإجابات داخل RPC/عملية خادمية واحدة أو آلية retry واضحة.

### 5. المساعد ليس محادثة ذكية فعلية

الإجابة المكتوبة تُصنف بواسطة بحث بسيط عن كلمات مفتاحية في `classifyFreeText()`. لا يوجد فهم للجملة، ولا أسئلة متابعة، ولا ذاكرة سياقية، ولا اكتشاف نية، ولا تلخيص شخصي مولد. كذلك لا يوجد API backend خاص بالمساعد.

**الإصلاح المقترح:** تحديد نسخة المنتج المطلوبة أولًا:

- إن كان المطلوب onboarding فقط، غيّر التسمية إلى “Guided Discovery” وكن صريحًا أنه اختبار إرشادي.
- إن كان المطلوب مساعدًا ذكيًا حقيقيًا، أضف endpoint خادميًا موثقًا، مصادقة، حدود استخدام، حفظًا انتقائيًا للسياق، prompts محمية، ومراقبة للتكلفة والسلامة.

### 6. التصنيف ثابت ومحدود

هناك أربعة عناصر فقط، والتعادل يميل إلى أول عنصر في الترتيب. الكلمات العربية محدودة، ولا توجد معالجة للهجات أو الأخطاء الإملائية أو الإجابات المختلطة. كما أن النتيجة تعتمد على اختيارات مصممة مسبقًا أكثر من اعتمادها على كلام المستخدم.

**الإصلاح المقترح:** حفظ درجات العناصر الأربعة، إظهار درجة الثقة، التعامل مع التعادل، وإتاحة تعديل النتيجة أو إعادة الإجابة قبل جعل الملف قابلًا للاكتشاف.

### 7. النتيجة تختفي تلقائيًا بعد 4.2 ثوانٍ

`renderResult()` يحول المستخدم تلقائيًا إلى Match بعد 4200ms. هذا قد يمنع قراءة النتيجة أو تعديلها، خصوصًا على الهاتف أو مع قارئات الشاشة.

**الإصلاح المقترح:** عدم الانتقال التلقائي. عرض زر “تابع إلى Match” فقط، أو جعل الانتقال اختياريًا مع عدّاد يمكن إلغاؤه.

### 8. البيانات الحساسة تحتاج سياسة أوضح

تاريخ الميلاد وإجابات الشخصية بيانات شخصية. توجد سياسات RLS للقراءة والكتابة الذاتية في migration، وهذا جيد، لكن لا توجد في المساعد واجهة لشرح مدة الاحتفاظ، حذف البيانات، تنزيلها، أو إخفاء ملف الاكتشاف بعد إكماله. كذلك لا يوجد سجل واضح لتاريخ تغييرات الإجابات.

**الإصلاح المقترح:** إضافة موافقة مختصرة قبل الإكمال، إعداد discoverable واضح، زر حذف/تنزيل بيانات الاكتشاف، وتوثيق سياسة الاحتفاظ.

## ما ينقص الموقع خارج المساعد

وفق الكود و`TODO.md` و`docs/phase1-audit-ar.md`، النواقص الأكبر هي:

1. ربط التسجيل وتسجيل الدخول بمسار Supabase Auth إنتاجي مكتمل بدل بقاء بعض التدفقات محلية/تجريبية.
2. رفع الصور والوسائط إلى Storage خاص بسياسات وصول صحيحة؛ معاينات الصور الحالية محلية، ولا يوجد نظام مكتمل لصور التحقق وكشف الوجه.
3. Match يحتاج بحثًا فعليًا حسب البلد والمدينة والعمر والتفضيلات، مع حقول ملف شخصية مكتملة.
4. الرسائل والإشعارات والمكالمات الصوتية ما زالت جزئيًا محاكاة محلية؛ لا يوجد Realtime ومزود مكالمات حقيقي مكتمل.
5. VIP Live والبث والدردشة والدفع والهدايا والسحب ما زالت scaffolding؛ يلزم مزود بث، webhooks، ledger idempotent، ومراجعة خادمية للسحب.
6. YouTube يحتاج ضبط `YOUTUBE_API_KEY` وbackend URL وrate limit قبل الإطلاق.
7. لا توجد لوحة إدارة مكتملة لإدارة المستخدمين والمحتوى والمساعد والأخبار والمعاملات والبث.
8. لا توجد أقسام Movies أو World News موسعة أو ألعاب الموقع المذكورة في التدقيق السابق.

## ترتيب التنفيذ المقترح

### المرحلة الأولى — إصلاحات يجب تنفيذها قبل اعتبار المساعد جاهزًا

- إصلاح استعادة `element` بعد refresh.
- إصلاح Start over بحذف/عزل الإجابات القديمة.
- إضافة حالة حفظ حقيقية مع retry ورسالة خطأ للمستخدم.
- إيقاف الانتقال التلقائي إلى Match.
- إضافة اختبارات تدفق: إجابات جاهزة، إجابات مكتوبة، refresh، تغيير جهاز، reset، فشل Supabase، والعمل دون speech synthesis.

### المرحلة الثانية — جعل المساعد أكثر فائدة

- إضافة نتيجة قابلة للتعديل مع درجات وثقة وتفسير واضح.
- إضافة أسئلة اختيارية للبلد والمدينة والعمر والتفضيلات إذا كانت مطابقة الأعضاء تعتمد عليها.
- ربط النتيجة مباشرة بملف المستخدم وMatch بطريقة ثابتة لا تعتمد على نص اللغة.
- إضافة حذف وتنزيل بيانات الاكتشاف وإعداد discoverable.

### المرحلة الثالثة — تحويله إلى AI حقيقي

- إضافة backend endpoint مصادق عليه بدل استدعاء نموذج من المتصفح.
- تعريف نطاق المساعد: onboarding، اقتراحات Match، أو دعم الموقع.
- إضافة rate limit، حجب البيانات الحساسة، سجل تدقيق، حدود تكلفة، وسياسة عدم اختلاق الأعضاء أو درجات التوافق.
- إبقاء الحسابات والمطابقات والقرارات الحساسة مصدرها قاعدة البيانات، وليس النص المولد.
